# Wrap an API as a plugin bundle

The original seat wrapped APIs into Cursor Agent Plugins (`plugin.json` + `mcp.json` +
skills); this repo has no Cursor loader, so the local equivalent is a DSH bundle:

| Cursor Agent Plugin | DSH equivalent |
|---|---|
| root `plugin.json` | `package.json` with `dsh.bundle.patch` → `cordis.patch.yml` |
| `skills/` + `mcp.json` | skills dir plus one `@deepseek-ai/dsh-mcp-client` row in a preset |
| `~/.cursor/plugins/local` | install the bundle into the active profile; new session |
| Marketplace / cursor.directory | external only — see `tinkabot-publish-plugin` |

## When to use

- The owner says "wrap", "expose", or "make a plugin for" an HTTP API, an OpenAPI file, or a
  local API client, and no MCP tools for it exist yet.
- A spec or client exists but sessions cannot call its endpoints.
- Before any plugin scaffolding: this skill picks the shape; scaffold only after it.

## Procedure

### A. Name the data shape first

1. `read` the spec/client and `grep` it for endpoints, auth schemes, pagination, rate limits,
   and the error envelope. If no spec exists, `bash` one read-only request against the API.
2. `write` the shape into `projects/<name>/notes/<api>-shape.md`: entities, ids, list and
   pagination, auth, write operations, error envelope, and two sample calls.
3. If auth, terms, or write safety are unclear, stop and ask the owner before building.

### B. Choose the smallest form that works

4. Use the decision table:

   | Owner needs | Form |
   |---|---|
   | Callable tools in sessions | preset + `@deepseek-ai/dsh-mcp-client` row |
   | Workflow instructions only | skills dir mounted by `customSkillDirs` |
   | Both | bundle with the preset, the MCP row, and the skills dir |
   | Rules/hooks/agents equivalents | ask the owner first; DSH has no hook surface |

5. Keep a public no-auth HTTP MCP server zero-dependency: one `server.mjs` launched with
   `node`, stdio transport, no SDK. Justify any dependency in one sentence in the note.

### C. Scaffold the bundle

6. `bash mkdir -p <bundle>`, then `write` `<bundle>/package.json`:

       {
         "name": "@local/<plugin-id>",
         "type": "module",
         "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
       }

   `team-bundle/` in this repo is generated by `scripts/build-bundle.mjs`; never hand-edit
   it. Put the new bundle at a path the owner accepts, outside `team-bundle/`.

7. `write` `<bundle>/cordis.patch.yml` with one `@deepseek-ai/dsh-agent-preset` insert whose
   `config.plugins` carries the seat plugins and exactly one MCP row:

       - id: mcp-<plugin-id>
         name: '@deepseek-ai/dsh-mcp-client'
         config: { serverName: <plugin-id>, transport: stdio, command: node, args: ["./server.mjs"] }

   Copy the row shape from a working row in the active profile's `cordis.patch.yml`; do not
   invent config keys. `serverName` is what makes tool names `mcp__<serverName>__<tool>`.

8. `write` `<bundle>/server.mjs` with one tool per data-shape operation, flat JSON arguments,
   and no secrets. When instructions belong to the plugin, also `write`
   `<bundle>/skills/<plugin-id>/SKILL.md` and mount it with `customSkillDirs`.

9. Scope check: the MCP row lives inside the preset, so its tools appear only in sessions
   started with that preset. Add a home-level insert only if the owner wants host-wide tools.

### D. Prove it locally (last step, before any publish talk)

10. Validate statically: `bash node scripts/validate-bundle.mjs` for this repo's generated
    bundle, or the harness loader's own parse check for a new bundle. A parse error stops.
11. Install the bundle into the active profile:
    `plugin_manager { action: "install_bundle", target: <absolute bundle path> }`.
    Report the install result verbatim; a failed install is `STATUS FAIL`.
12. Open a **new** session, pick the preset in the picker, and call one tool
    `mcp__<serverName>__<tool>`. `PASS` needs all three: preset visible in the new session,
    tool listed, and the call returned real data.
13. Record the proof in the note: bundle path, version, install result, preset name, tool
    name, sample call and output, and `PASS | FAIL | BLOCKED`.

## Output

- Artifacts: `<bundle>/package.json`, `<bundle>/cordis.patch.yml`, `<bundle>/server.mjs`,
  optional `<bundle>/skills/<plugin-id>/SKILL.md`, and
  `projects/<name>/notes/<api>-shape.md` holding the data shape plus the proof record.
- Every MCP row has a unique `serverName` and no dependency beyond the zero-dep rule.
- The proof record ends with `PASS | FAIL | BLOCKED` and the exact new-session evidence.
- Handoff to the Lead: bundle path, data shape in one line, proof word, publish state `none`.

## Failure handling

- Spec incomplete, auth unknown, or writes risky → `STATUS BLOCKED`, one `ask_user_question`
  with 2–4 options; never invent endpoints or an auth scheme.
- The MCP row does not mount → report the exact row and loader error; check `serverName`
  collision and preset scope before retrying. Do not fake a working tool.
- A dependency is genuinely required → justify it in one sentence; if the owner refuses,
  `STATUS BLOCKED` rather than shipping a heavier bundle.
- Install succeeds but the new session shows no preset → `STATUS FAIL`, not `PASS`.
- The owner asks to publish while wrapping → stop; switch to `tinkabot-publish-plugin`.
