# 文档管理机制（DOC_PROTOCOL）

> 维护：Lead ｜ 版本 v1（2026-11-05）｜ 来源：借鉴 `zq/.devenv/` 的文档治理实践
> 本文只回答一件事：**团队的事实、状态、过程、证据分别写在哪个文件里，谁写，什么时候写。**
> 任何角色开工前读一次；写文档前对照 §3 归属表。

---

## 1. 四条第一原则

1. **一物一源（SSOT）**：一个事实只有一个归属文档。其它文档**只引用，不复制**。
   发现两处不一致 → 以 SSOT 为准，修正引用方；不要在第三个地方再写一遍。
2. **四态分离**：**现状**（现在是什么）≠ **待办**（还要做什么）≠ **做法**（怎么做）≠ **证据**（为什么这么判断）。
   四者绝不混写。混写的直接后果：下一个人分不清"已完成的结论"和"当时的猜测"。
3. **裁决留痕**：任何用户裁决、团队裁决，都写成一行带日期的记录，并注明**取代了什么**。
   规则冲突时，**日期新的胜**；没有记录的"大家都知道的规矩"不存在。
4. **数字说话**：验收用基线数字（如 `health 49/49`、`chains 20/20`、`−84 行`），不用形容词。
   状态里必须带"最近一次验证时间"，否则这条状态不可信。

## 2. 文档分层（两个区）

### 2.1 团队区 `team/` — 描述"我们怎么协作"

| 文档 | 回答的问题 | 维护者 | 何时更新 |
|---|---|---|---|
| `team/TEAM_PROMPT.md` | 团队怎么组建、怎么协作、红线是什么 | Lead | 规则变化时 |
| `team/ROLE_PROMPTS.md` | 每个角色干什么、边界、验收、写哪 | Lead | 角色变化时 |
| `team/DOC_PROTOCOL.md` | 文档怎么管（本文） | Lead | 治理变化时 |
| `team/BOARD.md` | 本轮任务板 + 归档 | Lead | 每轮结束 |
| `team/personas/<id>.md` | 角色人格与常驻记忆 | Lead | 人格变化时 |
| `team/skills/<id>/**` | 角色可执行流程 | 该角色 | 流程变化时 |

### 2.2 项目区 `projects/<name>/` — 描述"这个项目现在怎么样"

| 文档 | 回答的问题 | 维护者 | 何时更新 |
|---|---|---|---|
| `project.md` | 目标、成功标准、Areas、不可变约定 | `pm` | 立项 / 范围变化 |
| `STATUS.md` | **现状**：基线数字、最后验证时间、已知偏差、已关闭事项 | `pm` | 每轮结束；状态变化时 |
| `tasks.md` | **待办**：任务卡（`Todo/In Progress/Blocked/Review/Done`） | `pm` | 每次状态变化 |
| `DECISIONS.md` | **裁决**：日期 + 内容 + 取代关系 | `pm` | 每次裁决 |
| `ITERATIONS.md` | 迭代索引：R1..Rn 一行一轮 | `pm` | 每轮结束 |
| `iterations/R<n>-YYYY-MM-DD.md` | **单轮记录**：目标/派工/产出/证据/遗留 | Lead | 每轮结束 |
| `notes/<role>/` | **过程证据**：受控归档（见 §4） | 各角色自己的子目录 | 按需 |
| `qa/` | 验收资产：`AC-PACK.md`、`run-YYYY-MM-DD-*.md` | `qa` | 每次运行 |

### 2.3 归属速查（谁写哪个）

| 角色 | 可写 |
|---|---|
| `lead` | `team/BOARD.md`、`projects/<p>/iterations/R*.md`、`team/*` 规范类 |
| `pm` | `projects/<p>/project.md`、`STATUS.md`、`tasks.md`、`DECISIONS.md`、`ITERATIONS.md` |
| `englead` | `notes/englead/`、代码与本地配置（按卡） |
| `audit` | `notes/audit/`、审计分支与提交 |
| `qa` | `projects/<p>/qa/**` |
| `tinkabot` | `notes/tinkabot/`、`plugins/**` |

**只有 `pm` 能改项目区那五个文件。** 别人要改 → `send_message` 给 pm 说明改什么；pm 改，不在别处另写一份。

## 3. 每轮迭代的固定动作（这是"维护迭代数据"的核心）

一轮 = 从 Lead 派工到 Lead 收口。每轮结束**必须**留下四项，缺一不可：

| 步骤 | 谁做 | 产物 |
|---|---|---|
| 1. 开轮 | `pm` | `tasks.md` 新增本轮卡；`STATUS.md` 顶部更新"最后验证时间" |
| 2. 施工 | 各角色 | 代码/配置改动 + `notes/<role>/` 证据 |
| 3. 收口 | `lead` | `iterations/R<n>-YYYY-MM-DD.md`（本轮记录） |
| 4. 结轮 | `pm` | `ITERATIONS.md` 加一行；`STATUS.md` 更新基线数字与偏差；`BOARD.md` 归档本轮 |

**单轮记录模板**（`iterations/R<n>-YYYY-MM-DD.md`）：

```markdown
# R<n> YYYY-MM-DD

## 本轮目标
- <一句话，可判定>

## 派工
| 卡 | Owner | write_scopes | 结果 |
|---|---|---|---|

## 产出
- <文件/提交/分支> — <一句话说明>

## 证据
- <命令 + 关键输出 / 报告路径 / 截图路径>

## 遗留
- <未完成项 → 是否已建卡>

## 本轮裁决
- YYYY-MM-DD <裁决内容>（由 <用户/lead>）
```

## 4. 防膨胀治理（硬规则）

> 借鉴 .devenv 2026-11-03 用户裁决：**一次性记录不再单独成文**。

1. **一次性排查 / 验证 / 修复 / 交接，不单独写报告。** 结论并入：
   - 做法类 → 对应 skill 的「常见坑」或 `RUNBOOK` 式章节；
   - 事实类 → `STATUS.md` 的「已知偏差」；
   - 规则类 → `DECISIONS.md`。
2. `notes/` 只收**四类**：① 事故复盘（需长期追溯）② 规则变更记录 ③ 跨人交接 ④ 被长期文档引用的证据。其余一律不进。
3. **同类问题只维护一份通用说明**，不按事件重复写。
4. 新增文档 **30 天无人引用即清理**；大体积证据先移到 `notes/_archive/` 再删索引项。
5. 每轮结束时 `pm` 做一次 30 秒体检：`notes/` 是否出现了第 5 类文件？有就合并不合规的那份。

## 5. 命名与路径约定

| 类型 | 路径 | 命名 |
|---|---|---|
| 单轮记录 | `projects/<p>/iterations/` | `R<n>-YYYY-MM-DD.md` |
| 过程证据 | `projects/<p>/notes/<role>/` | `YYYY-MM-DD-<slug>.md` |
| 事故复盘 | 同上 | `POSTMORTEM-YYYY-MM-DD-<slug>.md` |
| QA 运行 | `projects/<p>/qa/` | `run-YYYY-MM-DD-<slug>.md` |
| AC 包 | `projects/<p>/qa/` | `AC-PACK.md`（单份，版本在文件内） |
| 截图 | `notes/<role>/screenshots/` | `YYYY-MM-DD-HHmm-<场景>-<序号>.png` |

**禁止**：`final.md`、`final2.md`、`new.md`、`temp.md`、`xxx-副本.md`。
版本靠 Git 与文件内「变更记录」小节，不靠文件名。

## 6. 提示词条款（可直接粘贴进角色 prompt）

以下四条是**压缩版**，用于注入每个角色的 spawn prompt；完整机制见本文正文。

```text
【文档纪律】
1. 一物一源：一个事实只写在一个归属文件里，别处只引用不复制。归属见 DOC_PROTOCOL §2.3。
2. 四态分离：现状写 STATUS、待办写 tasks、做法写 skill、证据写 notes。不要把结论、猜测、待办混进同一段。
3. 裁决留痕：任何裁决写成「YYYY-MM-DD <内容>（取代 <旧口径>）」，写进 DECISIONS.md。新裁决胜旧裁决。
4. 数字说话：验收写基线数字与验证时间，不写形容词。没验证过的东西前缀 `guess:`。
```

## 7. 与任务板的分工

- **任务板（`team_task_*`）**：实时协作，短生命周期，用于认领/阻塞/依赖。
- **项目账本（`projects/`）**：持久记录，长生命周期，用于下一个人/下一个会话接手。

判定：**换了会话还需要知道的事 → 写账本；只在本次会话内协调的事 → 写任务板。**
两者都要写的是「卡的状态」：任务板更新 owner/阻塞，账本更新 Status 与证据。
